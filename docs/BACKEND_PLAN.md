# AP Food + FIF · Backend delivery plan

Start with the [backend guide](BACKEND.md) for the current migrations, API contracts, and verification commands. The [MVP](MVP.md) defines the release scope. The plan below carries it through hosted integration and the two follow-on FIF features.

## FIF features

| Feature | What it delivers | Release |
| --- | --- | --- |
| SmartQueue | Quotes feasible 15-minute pickup windows from stall hours, lead time, stock, and capacity. Checkout revalidates the quote and reserves stock and capacity atomically. | Hackathon |
| FlowSense | Shows upcoming app pickups and committed kitchen load by stall and zone. Recommends lower-load alternatives from available windows. | Hackathon |
| InsightAI | Ranks evidence-backed actions for Student Pick, Vendor Shift Brief, and Admin Ops Desk. Gemini ranks candidates generated by the app, with a deterministic fallback. | Hackathon |
| DemandSense | Forecasts AP Food order arrivals, with source, coverage, and freshness labels. | Follow-on |
| ScheduleSync | Ranks feasible pickup windows around an opt-in timetable and walking buffers. | Follow-on |

## 1. Hosted order-to-receipt

- Apply the versioned migrations to the dedicated hosted Supabase demo and seed fictional student, vendor, and admin roles. Keep bootstrap credentials local.
- Connect the existing screens through one adapter with explicit mock and Supabase modes. Wire auth, catalogue, checkout, tracking, kitchen, and pickup first. Keep the cart editable in the browser and use backend quote prices and pickup timestamps. Preserve the cart on conflicts and expose the retry action.
- Use private Realtime invalidations with an authorised refetch and scoped polling fallback. Then connect vendor settings and admin products, stall controls, audit, and finance. Recognise receipts at collection. Keep pending counter payments separate and preserve historical price and zone snapshots.
- Gate on a three-role walkthrough in separate authenticated sessions. Verify one receipt at the quoted price, denial for unrelated students and stalls, a real WebSocket subscription, and the existing concurrent HTTP smoke test.

## 2. Isolated traffic scenarios and InsightAI

The [local traffic CLI](BACKEND.md#rehearse-traffic-locally) exercises Light, Medium, and Heavy through the versioned checkout and fulfilment functions. The remaining simulation work covers hosted run persistence, scope, and dashboards.

The local Traffic Lab exposes the CLI results on the admin traffic page. The three hosted home screens now call the server-owned FIF endpoint. Candidate generation, optional Gemini ranking, evidence validation, role checks, database-backed usage limits, scoped caching, and the rules fallback are implemented. Rules are active until a Gemini key is configured. Hosted simulation persistence is still a separate feature milestone.

- Give every simulation run its own fictional stall and menu copies, scoped simulator accounts, and attempt records. Derive provenance from authorised run membership and stall scope. Default catalogue, history, finance, and traffic to the standard demo. Filter explicit run views before aggregating.
- The CLI uses the same authenticated checkout and fulfilment paths as the app. Target a five-unit bucket with one initial request for Light, three for Medium, and 12 concurrent requests for Heavy. Heavy should reserve five units and return seven slot conflicts under the controlled fixture. Requote a bounded subset into later windows and keep a nearby stall lightly loaded.
- Persist exact checkout inputs and idempotency keys before dispatch. Replay uncertain attempts with the same payload. A completed run ID returns its recorded result. Track attempted, placed, conflicted, rerouted, collected, and cancelled counts. Display source labels in traffic and finance. Treat the seed as reproducible request intent, with live timing determining concurrent outcomes.
- Implemented: `POST /api/fif/recommendations` for all three role panels. Only aggregate signals and opaque IDs go to Gemini. Candidate IDs and evidence references are validated; visible facts and links come from server evidence. Complete the live provider walkthrough when a server key is added.
- Gate on an interrupted run resuming without duplicates, cross-run denial, unchanged standard-demo stock and cashflow, and three panels showing the recommendation source and evidence. Test Gemini success, timeout, invalid output, and missing-key fallback.

## 3. DemandSense and ScheduleSync

- **DemandSense.** Store versioned forecast snapshots by stall or zone, 15-minute bucket, source, and generation time. Schedule a recency-weighted weekday/time-of-day forecast, with meal-period or zone fallbacks for sparse data. Evaluate chronological holdouts against a naive baseline using MAE and WAPE before feeding forecasts into FIF. Keep synthetic history separately labelled. Show insufficient or stale data explicitly.
- **ScheduleSync.** Start with manual opt-in timetable entry, owner-only access, and deletion. Apply a configurable walk estimate and a default ten-minute buffer before the next class. Rank windows already deemed feasible by SmartQueue. Add bounded calendar import after overlap, timezone, and deletion tests pass. Keep timetable data within the scheduling service.
